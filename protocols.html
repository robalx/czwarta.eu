Protokoły

Podstawowe protokoły i standardy

Cztery warstwy komunikacji z kamerą IP — od sterowania (ONVIF), przez transport (RTSP), po odtwarzanie w przeglądarce (HLS/WebRTC) i sesje audio (SIP).

4 protokoły+ rekomendator

Kamera IP to nie czarna skrzynka — mówi kilkoma standardami. Wiedza o tym, który protokół za co odpowiada, rozwiązuje 90% problemów „nie widzę obrazu". Poniżej cztery warstwy, które spotkasz w niemal każdym urządzeniu.

ONVIF

Warstwa sterowania: discover, konfiguracja, PTZ, zdarzenia.

RTSP / RTP

Warstwa transportu: strumień audio/wideo w czasie rzeczywistym.

RTMP/HLS/WebRTC

Warstwa odtwarzania: przeglądarka i nowoczesne klienty.

SIP

Warstwa sesji: dwukierunkowe audio, domofony.

ONVIF #

ONVIF (Open Network Video Interface Forum) to otwarty standard komunikacji z kamerami IP, niezależny od producenta. Dzięki niemu można w jednolity sposób odkrywać urządzenia w sieci, konfigurować strumienie, sterować mechaniką PTZ oraz odbierać zdarzenia (rover ruchu, wejście/wyjście, alarmy). Standard jest zorganizowany w profilach, które określają konkretne możliwości urządzenia — warto sprawdzić, który profil deklaruje Twoja kamera, zanim zaczniesz pisać kod.

  • Profile S/G/T — streaming IP, PTZ i zdarzenia (najczęstsze w kamerach konsumenckich/pro).
  • Profile C/A — access control i analiza obrazu (edge analytics).
  • Profile Q — discovery zaawansowane, QoS, TLS.
python
from onvif import ONVIFCamera

cam = ONVIFCamera("192.168.1.10", 80, "user", "pass")
media = cam.create_media_service()
streams = media.GetProfiles()

token = streams[0].token
uri = media.GetStreamUri({"StreamSetup": {"Stream": "RTP-Unicast", "Transport": {"Protocol": "RTSP"}}, "ProfileToken": token})
# -> uri.Uri  ==  rtsp://.../Streaming/Channels/101
Discovery bez ONVIF

Samo odkrywanie urządzeń odbywa się po SOAP/multicast (port 3702, grupa 239.255.255.250). W zamkniętej sieci lepiej od razu wylistować nmap -p 554,3702,80,443 i zgadywać URL.

RTSP / RTP #

RTSP (Real-Time Streaming Protocol) to protokół sterowania strumieniem — „odtwarzacz" negocjuje z kamerą sesję, a właściwe pakiety audio/wideo płyną protokołem RTP, zazwyczaj przez UDP lub multiplexowane po TCP (rtsp_transport tcp). Większość kamer IP udostępnia strumień pod klasycznym adresem rtsp://ip:554/..., gdzie końcówka ścieżki zależy od producenta.

bash
# anatomia URL RTSP
rtsp://user:pass@192.168.1.10:554/Streaming/Channels/101
         ↑      ↑              ↑   ↑
   autoryzacja    host          port  ścieżka (zależna od producenta)

# popularne ścieżki
Hikvision  /Streaming/Channels/101
Dahua      /cam/realmonitor?channel=1&subtype=0
Reolink    /h264Preview_01_main
Generic    /stream1  /h264/channel1
UDP vs TCP

RTSP po UDP ma niższe opóźnienie, ale gubi pakiety w gorszych sieciach i bywa blokowane przez NAT. W praktyce -rtsp_transport tcp jest bezpiecznym domyślnym wyborem do nagrywania i analizy.

RTMP / HLS / WebRTC — odtwarzanie w przeglądarce #

RTSP nie jest natywnie obsługiwany w przeglądarce. Aby pokazać obraz w webowym podglądzie, transkoduje się strumień do formatu przeglądarkowego: najczęściej HLS, dla niskich opóźnień WebRTC, a do re-streamingu do CDN-ów RTMP. HLS jest dziś standardem w nowoczesnych systemach webowych, bo działa w <video> z minimalną ilością JavaScriptu (hls.js).

ProtokółLatencjaPrzeglądarkaTypowy use-case
RTMP~2–5 snie (flash era)ingest do serwerów streamingowych / CDN
HLS~2–10 snatywnie + hls.jspodgląd webowy, dashboardy, nagrania
LL-HLS~1–2 shls.jskompromis latency/compat
WebRTC<500 msnatywniedwukierunkowe, live, interkom
bash
# RTSP -> HLS (podgląd w 
ffmpeg -rtsp_transport tcp -i rtsp://user:pass@192.168.1.10:554/stream1 \
  -c:v copy -c:a aac -f hls -hls_time 4 \
  -hls_list_size 4 -hls_flags delete_segments stream.m3u8

SIP — dwukierunkowe audio #

SIP (Session Initiation Protocol) to protokół sygnalizacyjny zapożyczony ze świata VoIP. W monitoringu pojawia się w domofonach IP i bramkach z dwukierunkowym dźwiękiem — zestawia sesję między urządzeniem a klientem (softphone, centrala, webowy interkom przez SIP↔WebRTC gateway). Pozwala na dwukierunkowe połączenie audio/wideo między urządzeniami i jest standardem otwartym, więc nie blokuje Cię u jednego producenta.
